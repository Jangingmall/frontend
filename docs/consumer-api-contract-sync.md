# 기존 화면의 최신 백엔드 API 연결

관련 이슈 #92. 프론트엔드 `dev@dc18fd8`, 백엔드 `develop@c4d3f52`를 비교했다. 기존 Figma 레이아웃·입력 항목을 유지하고, 실제 서버가 지원하는 동작과 응답 매핑만 추가한다. 이전 PR #87의 상품·카트·결제·계정 연동은 유지한다.

## 변경한 계약

| 기존 화면      | 최신 백엔드 계약과 동작                                                                                                                                                                                        |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 이메일 가입    | `POST /api/member/email/verification-code`, `/email/verify`에 이메일/코드를 전송한다. 발송 성공의 `data:null`을 허용하며 서버 TTL 300초를 사용한다. 인증 시도가 코드를 소비하므로 실패하면 재발송을 안내한다.  |
| 가입 완료      | `POST /api/member/signup`의 `accessToken:null`은 세션 미발급이다. 별도 로그인 요청 성공 후에만 로그인 상태로 전환한다. 로그인 실패 시 가입을 재전송하지 않고 로그인 화면으로 안내한다.                         |
| 주문 취소      | `POST /api/payments/orders/{id}/cancel`, 본문 없음. 결제 전 CREATED 주문 전체만 취소한다. 결제 후 취소는 안내를 표시하고 요청을 차단한다.                                                                      |
| 배송지 변경    | 회원 배송지를 조회해 동일한 주소를 재사용하거나 새 주소를 등록한 뒤 `PATCH /api/payments/orders/{id}/shipping-address`에 `{addressId}`를 보낸다. CREATED/PAID 상태에서 사용한다. 기존 주소는 수정하지 않는다.  |
| 구매 확정      | 목록·상세의 기존 버튼에서 주문 전체 적용과 교환·환불 불가를 확인한 뒤 `POST /api/payments/orders/{id}/purchase-confirmation`을 호출한다. DELIVERED 주문만 가능하다. 중복 제출을 막고 실패 시 재시도할 수 있다. |
| 주문 상태·후기 | PURCHASE_CONFIRMED를 별도 상태/필터로 사용한다. 주문·후기 캐시를 갱신한다. ImageRef의 variants, legacy URL, 구조화된 옵션, 0.5 단위 별점을 기존 화면 모델로 변환한다.                                          |

취소·구매 확정 응답의 주문 ID와 상태, 배송지 변경 응답의 주문/배송지 ID를 검증한다. 주소 생성 후 주문 변경이 실패해도 재시도 시 같은 주소를 재사용한다. 이메일 인증 요청 중 이메일 변경과 가입 중복 제출도 차단한다.

## 유지한 화면과 서버 제약

- 기존 취소 사유·사진 UI는 유지한다. 실제 취소 API가 받지 않는다는 안내를 표시하고 사진 선택/업로드를 막는다. 사유를 서버에 저장한 것처럼 표시하지 않는다.
- 미지원 상품 필터·정렬·옵션, 비밀 문의 제한 등 기존 화면을 삭제하거나 재설계하지 않는다.
- 공개 상품 후기 API가 반환하는 사진 ID를 임의의 URL로 만들지 않는다. 실제 URL이 있는 사진만 표시한다. 옵션 이름이 없으면 내부 ID를 사용자에게 대신 보여주지 않는다.
- 백엔드 Signup 서비스는 이메일 인증 완료 여부를 가입 시 다시 검증하지 않는다. 화면에서는 인증을 요구하지만 서버 검증 보강은 백엔드 작업이다.
- 인증번호 발송·OAuth·Toss 결제·배송 조회의 실제 외부 서비스 성공 여부는 준비된 서버와 테스트 계정으로 별도 확인해야 한다.

## 실제 API로 실행하기

프론트엔드 주소와 백엔드 주소는 다를 수 있다. 브라우저는 프론트엔드의 `/api/*`로 요청하고, Next.js가 `API_BASE_URL`의 백엔드로 전달한다. ECR 이미지 주소는 API 서버 주소가 아니다.

로컬 `.env.local` 또는 배포 환경에 다음 값을 설정한다. 비밀값은 저장소에 커밋하지 않는다.

```dotenv
# 실제 백엔드 origin으로 변경. /api 접미사와 마지막 /는 넣지 않는다.
API_BASE_URL=https://backend.example.com
# 빈 값 또는 변수 제거. enabled는 MSW 시연, disabled 문자열은 허용하지 않는다.
NEXT_PUBLIC_API_MOCKING=
REVALIDATE_WEBHOOK_SECRET=<배포 환경에서 사용하는 비밀값>
NEXT_PUBLIC_TOSS_CLIENT_KEY=<Toss 테스트용 공개 클라이언트 키>
```

`NEXT_PUBLIC_API_MOCKING`과 rewrite 대상은 빌드에 반영되므로 변경 후 다시 빌드/배포한다. MSW 확인은 `NEXT_PUBLIC_API_MOCKING=enabled`로 별도 빌드한다. 실제 API 모드에서 목업 응답으로 자동 대체하지 않는다.

## 검증 범위

- 실제 모드의 계약 테스트: 엔드포인트·요청 본문·null 응답·가입 후 로그인 실패·주문 상태 충돌·잘못된 주문 ID 응답·배송지 재시도·이미지/옵션/별점 매핑.
- 전체 단위/컴포넌트 테스트와 타입·린트·빌드 검사, MSW 모드의 브라우저 회귀 흐름.
- 계약 테스트는 백엔드 소스를 기준으로 작성한 MSW 응답을 사용한다. 배포된 실서버 호출 성공을 의미하지 않는다. 이번 작업에서는 접근 가능한 실제 API 주소와 테스트 계정이 없어 실서버 메일/결제 성공을 확인하지 못했다.
