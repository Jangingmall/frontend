## 2. 브랜치 전략

### 2.1 브랜치 구조

| 브랜치         | 역할                                 |
| -------------- | ------------------------------------ |
| `main`         | 배포 가능한 안정 버전                |
| `dev`          | 기능을 통합하는 메인 개발 브랜치     |
| `feat/기능명`  | 기능 추가                            |
| `fix/버그명`   | 버그 수정                            |
| `chore/작업명` | 설정, 패키지, 환경 구성 등 기타 작업 |

### 2.2 네이밍 규칙

- 영어 소문자를 사용한다.
- 여러 단어는 하이픈으로 구분한다.
- 브랜치 이름만으로 작업 목적을 이해할 수 있게 작성한다.
- 예: `feat/user-login`, `fix/scroll-bug`, `chore/eslint-setup`

### 2.3 분기·병합 방향

```
dev → feat/fix/chore → dev → main
```

- `feat`, `fix`, `chore` 브랜치는 항상 `dev`에서 분기한다.
- 작업 브랜치는 리뷰를 거쳐 `dev`로 병합한다.
- `dev` → `main` 병합은 배포 시점에 진행한다.
- 작업 브랜치는 `dev` 병합 후 삭제한다.
- 하나의 브랜치에서는 하나의 기능·작업만 처리한다.

## 3. 커밋 컨벤션

### 3.1 형식

```
type: subject
```

```
feat: 사용자 로그인 기능 추가
fix: 모바일 화면 스크롤 오류 수정
chore: ESLint 설정 추가
```

형식은 `scripts/verify-commit-msg.ts`의 `commit-msg` 훅이 검증한다.

### 3.2 Type

| Type       | 설명                                          |
| ---------- | --------------------------------------------- |
| `feat`     | 기능 추가                                     |
| `fix`      | 버그 수정                                     |
| `style`    | 포맷팅 등 기능 변경 없는 스타일 수정          |
| `refactor` | 기능 변경 없는 코드 구조 개선                 |
| `chore`    | 설정·패키지 등 다른 Type에 해당하지 않는 작업 |
| `docs`     | 문서 작성·수정                                |
| `test`     | 테스트 작성·수정                              |

### 3.3 Subject 규칙

- 한국어·영어 모두 사용할 수 있다.
- 현재형·단답형으로 작성한다.
- 50자 이내로 간결하게 작성한다.
- 마침표를 붙이지 않는다.
- 커밋 메시지는 헤더만 작성한다.

### 3.4 커밋 단위

- 하나의 커밋에는 하나의 목적만 담는다.
- 서로 되돌릴 가능성이 있는 변경은 분리한다.
- 목적이 다른 변경(기능 구현, 리팩터링, 문서 수정)을 한 커밋에 섞지 않는다.

## 4. GitHub 운영

PR·이슈 템플릿은 `.github/`에 있다.

- PR: `.github/PULL_REQUEST_TEMPLATE.md`
- 이슈: `.github/ISSUE_TEMPLATE/작업-이슈.md`

다음 항목은 별도 **GitHub Rule**에서 정의한다(팀 논의 후 문서화 예정).

- 리뷰어 수와 Approve 기준, Change Request 처리 방식
- 병합 방식과 작성자 self-approve 제한
- `main`·`dev` 브랜치 보호 규칙
- 필수 CI 검사
- Issue 운영 방식

CI 파이프라인 구성은 [testing.md](testing.md) §7.
