Figma 페이지 `889:59175`의 장바구니 `1906:46966`, 주문 결제 `2169:61310`, 주문 완료 `1906:50709`와 관련 옵션·삭제·로그인·실패 상태를 기준으로 확인했다. 실제 API 모드에서도 디자인 영역을 유지하며, 데이터가 없을 때 임의의 상품·가격·계좌·결제 성공을 만들지 않는다.

## 백엔드 코드 확인

로컬 백엔드 `0e7a1a0`의 `PaymentController`, `AddressController`, `JdbcCheckoutCatalog`를 확인했다. 옵션 변경 엔드포인트 자체는 있지만 `JdbcCheckoutCatalog.quote`가 옵션 가격·유효성을 검증하지 않고 `describe`가 빈 옵션 목록을 반환한다. 따라서 엔드포인트 존재만으로 옵션 변경을 활성화하지 않는다. 배송비 역시 현재 카탈로그 코드가 0을 반환하며 프론트에서는 해당 API 값을 사용한다.

## 검증과 한계

- typecheck, lint, 전체 단위 테스트 165개 파일 / 1,011개 통과.
- 결제·완료 화면 E2E 6개 통과: 데스크톱, 좁은 화면, 입력·주소·메모·목업 무통장입금·실패 상태.
- 실제 로컬 Docker 백엔드로 장바구니 상품·합계와 결제 화면의 회원 정보·배송지·주문 작품 표시 확인.
- 빈 선택·API 오류에도 레이아웃 유지, 주소 저장 실패 시 주문 미생성, 서버 금액 변경 재확인, 미결제 주문 완료 차단 테스트 포함.
- 로컬 Toss 키가 미설정되어 실제 PG 승인 종단 검증은 미완료. 결제 성공을 가정하지 않는다.

## 상품 상세 구매 진입

실제 상품 상세의 장바구니 버튼은 비회원/회원 모두 `POST /api/payments/cart/items`를 호출한다. 구매하기는 로그인 확인 후 같은 API 응답의 장바구니 항목 ID로 주문서에 진입한다. 로컬 백엔드가 같은 작품의 수량을 합산하므로, 요청 수량과 응답 수량이 다르면 합산 수량 확인창에서 계속 주문하거나 장바구니에서 수량을 조정한다. API 실패 시 이동하지 않으며 중복 클릭을 차단한다.

현재 실제 카탈로그가 지원하는 기본 상품을 연결했다. 옵션 그룹이 존재하는 상품, 품절·재고 미확인 상품은 지원·재고가 확인되기 전까지 주문하지 않는다. 목업 옵션 UI는 유지한다.
