# 스테이징 실제 API 검증 (2026-09-29)

## 후속 구현 범위 (이슈 #113)

사용자 요청에 따라 백엔드 수정 없이 가능한 부분만 연결한다. 아래 실서버 검사 기록은 연결 전 기준이며, 이번 프론트 변경 검증과 구분한다.

| 항목               | 최종 처리                                                                                                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장바구니 옵션 변경 | `PATCH /api/payments/cart/items/{cartItemId}/options` 연결. 수량과 기존 텍스트 입력만 편집하고 선택형 옵션 ID는 유지한다. 서버가 선택지 목록을 제공하지 않으므로 선택형 변경은 미연결. |
| 상품 문의          | `POST /api/products/{productId}/questions` 공개 문의 작성만 연결. 1~1000자와 `secret: false` 계약을 적용한다. 비밀 답변 노출 문제로 GET 목록 조회와 비밀 문의는 미연결.                |
| 결제 후 취소       | 주문 응답에 취소용 paymentId가 없어 미연결. 기존 CREATED 주문 취소는 유지.                                                                                                             |
| 가상계좌           | 백엔드가 발급과 입금 완료를 구분하지 않고 PAID 처리하므로 미연결.                                                                                                                      |
| 인기 정렬          | 사용자 후속 요청에 따라 `sort=POPULAR`를 전송하고 서버가 반환한 순서를 그대로 표시한다. 기본 정렬은 최신순 유지.                                                                       |
| 네이버 로그인      | 인증 처리에서 카카오만 허용하므로 비활성화 유지.                                                                                                                                       |

공개 문의 POST와 텍스트 옵션 편집은 실제 계약을 사용하는 자동 테스트로 검증한다. 판매자에게 테스트 문의를 전송하지 않았으며 실제 문의 저장, 값이 있는 텍스트 옵션 저장의 실서버 검증은 미완료다. 아래 장바구니 수량 저장 실검증과 혼동하지 않는다.

## 연결 전 판정 기준과 결과

사용자 요청: API가 존재하고 기존 화면이 요청·응답에 맞게 설계된 항목만 실제 서버로 검증한 뒤 활성화한다. HTTP 200만으로 기능을 지원한다고 판정하지 않는다.

- 프론트 기준: dev `27a012b` (PR #112 병합).
- 대상: https://stg.midam.store / https://api.stg.midam.store
- 공개 계약: https://jangingmall.github.io/backend/summary.html 및 상세 OpenAPI.
- 백엔드 코드 대조: develop `bfb9e8452f1a305e334f41c040389ffe30891641`. 배포 바이너리가 이 커밋과 동일하다는 보장은 없다.
- 실제 스테이징 HTTP와 로그인된 Chrome에서 확인했다. MSW·응답 대역은 사용하지 않았다.
- 기존 실제 API 연결은 유지한다. 비활성화된 기능 중 **기존 화면 계약 일치와 실제 동작을 모두 확인한 신규 활성화 대상은 없었다.**

## 토스창이 열리지 않는 실제 원인

기존 실제 주문 화면에서 테스트 상품을 선택하고 저장된 테스트 배송지·카드 결제를 사용했다.

1. `POST https://stg.midam.store/api/payments/orders` → 201.
2. `POST https://stg.midam.store/api/payments` → 201, 동일 주문 재시도에서는 200.
3. 프론트가 응답의 `tossClientKey`로 기존 Toss SDK 결제창을 요청한다.
4. `https://apigw-sandbox.tosspayments.com/payment-gateway-window/open/pg-window/v1/px-payment-parameters` → **401**.
5. 응답: `UNAUTHORIZED_KEY`, `인증되지 않은 시크릿 키 혹은 클라이언트 키 입니다.`

클라이언트 키 종류는 `test_ck`였으나 토스가 유효한 키로 인정하지 않았다. 사용자는 스테이징이 테스트 키 환경임을 확인했다. 토스 공식 문서도 해당 오류를 잘못된 API 키로 설명한다: https://docs.tosspayments.com/guides/v2/payment-window/integration

백엔드 결제 준비 응답에 유효한 해당 상점의 테스트 클라이언트 키가 공급되는지 확인하고, 승인용 시크릿 키도 같은 상점·환경의 키인지 확인해야 한다. 시크릿 키를 프론트에 넣거나 문서 예제 키로 임의 대체하지 않았다. 키 교정 후 결제창 → 테스트 승인 → 주문 PAID → 테스트 결제 취소까지 재검증해야 한다.

처음 백엔드 origin에 직접 주문 생성 요청을 했을 때는 브라우저 fetch 실패가 발생했다. 실제 프론트처럼 `/api/payments/*`는 same-origin 프록시를 사용하자 성공했다. 이를 현재 프론트 주문 생성 결함으로 분류하지 않는다.

## 비활성화 유지 이유

| 항목                                                                                                              | API 존재 여부와 현재 제약                                                                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장바구니 옵션 변경                                                                                                | PATCH는 존재하지만 실제 상품 상세에는 선택 가능한 옵션 그룹·선택지 목록이 없다. 기존 옵션 대화상자는 목업 문자열 기반이며 API의 optionGroupId/choiceId를 반환하지 않는다. 수량 변경 성공만으로 옵션 변경을 켜지 않는다. |

| 네이버 로그인                                                                                                     | 리다이렉트 엔드포인트는 존재하나 OAuthIdentity가 kakao만 허용하는 코드가 남아 있음.                                                                                                                                     |

| 인기 정렬                                                                                                         | 초기 검사에서는 POPULAR가 상품 ID 역순이라 보류했다. 후속 요청으로 서버 정렬 그대로 연결했다.                                                                                                                           |
| 홈 베스트·기획전, 소재·공예·포장 필터, 판매·찜 정렬, 재입고 알림, 사진 후기 필터, 할인코드·쿠폰·적립금, 취소 사진 | 현재 화면 요구에 맞는 실제 계약을 확인하지 못함. 소재 목록 API 존재는 상품 소재 필터 지원의 근거가 아님.                                                                                                                |
| preview=1 상세                                                                                                    | 명시적인 시연 진입이며 실제 API 기능이 아니므로 차단 유지.                                                                                                                                                              |

## 데이터 정리

테스트 주문 5·6은 모두 CANCELED로 확인했다. 임시 장바구니 항목 5·6·7과 배송지 3·4·5를 삭제했다. 최종 장바구니에는 기존 항목 3만 남고, 배송지는 검사 전과 같은 0개다. 취소된 테스트 주문 기록은 서버에 남는다. 실제 결제 승인·과금·환불은 발생하지 않았다.

## 공개 계약 재검사

PowerShell:

```powershell
$env:API_BASE_URL = 'https://stg.midam.store'
$env:LIVE_PRODUCT_ID = '730'
npm run verify:live-api
```

스크립트는 현재 프론트의 Zod 스키마를 재사용하며 공개 GET만 실행한다. 인증 정보, 서비스워커, 목업, 주문·결제 변경을 사용하지 않는다. 실패 시 종료 코드 1을 반환한다. 선택한 상품이 삭제되거나 판매 중지되면 검증할 공개 상품 ID를 변경한다. 빈 후기·장바구니 응답의 통과는 비어 있지 않은 데이터나 쓰기 동작의 검증을 대신하지 않는다.

- `npm run test -- --maxWorkers=4`: 212파일, 1,289개 통과.
- `npm run build`: 통과.

- 별도 코드 리뷰: 수정이 필요한 문제 없음.

## 인기순 후속 반영

사용자 요청으로 인기순을 활성화했다. 프론트가 `sort=POPULAR`를 전달하며 서버 결과를 재정렬하지 않는다. 상품 ID 역순이라는 기존 백엔드 구현은 변경하지 않았다. 실서버 POPULAR 요청은 HTTP 200 및 목록 스키마 검증을 통과했으며 인기 집계 정확성을 검증한 것은 아니다. 공개 GET 검사 범위는 11개로 늘었다.
