# API / MSW 두 모드 통합 설계

상태: 사용자 검토용. 제품 코드는 아직 변경하지 않았다.

## 요청과 기준

- MSW 버전: 모든 애플리케이션 API 동작을 MSW로 시연한다.
- API 버전: 구현된 백엔드 API를 사용하고, 없는 기능은 MSW로 시연한다.
- 같은 화면과 입력 항목을 유지한다. API 소스에 따라 페이지를 숨기지 않는다.
- 기준은 백엔드 구현 대조 문서(2026-09-28, backend `48417a6`)와 실제 코드다. 기존 FE 문서의 오래된 미지원 설명은 갱신한다.
- 사용자가 범위를 현재 만들어진 화면 전체로 확정했다. 현재 실행 브랜치 `feat/consumer-api-contract-sync`의 기존 화면을 대상으로 하며, 판매자·관리자 신규 화면은 만들지 않는다.
- 기존 PR 리뷰 수정과 별개 변경으로 관리한다. 이 설계 검토 과정에서 새 이슈/PR을 만들지 않는다.

## 연결 방식

API가 실패했을 때 목업으로 바꾸는 방식 대신, 기능별로 사용할 소스를 미리 지정한다. 장애 때도 성공처럼 보이는 일을 방지하고, 백엔드 구현 여부와 연결 상태를 추적할 수 있기 때문이다.

1. 중앙 기능 목록에 기능 키, 문서 경로, HTTP 메서드, 실제 경로, 백엔드 구현 상태, 화면, API 모드 소스, 목업 핸들러를 기록한다.
2. MSW 모드는 전체 핸들러를 활성화한다. 기존 로컬 상태로만 성공시키는 장바구니·결제 등의 동작도 MSW 요청을 거치게 한다.
3. API 모드는 명시적으로 지정한 미구현 기능의 핸들러만 활성화한다. 구현된 API 요청은 백엔드로 보낸다.
4. 브라우저 Worker와 서버 렌더링용 Node MSW가 같은 소스 판정 목록을 공유한다. 첫 요청 전에 초기화를 마친다.
5. 401/403/404/409/500, 타임아웃, 잘못된 응답은 실제 오류로 처리한다. 404가 곧 미구현 API라는 뜻은 아니다.
6. API가 빈 목록이나 nullable 필드를 반환한 경우에는 그 값을 존중한다. 없는 API의 목업과 실제 데이터의 빈 값을 구분한다.
7. 백엔드 DTO와 MSW DTO는 각각 검증하고 같은 화면 모델로 변환한다. 실제 DTO를 목업의 모양에 맞게 추정하지 않는다.

## 모드 설정과 상태

- 명시적인 `NEXT_PUBLIC_DATA_MODE=msw|api`를 도입한다. 기존 `NEXT_PUBLIC_API_MOCKING=enabled`는 이전 설정 호환용으로 해석하되 상충한 설정은 검증 오류로 알린다.
- API 모드는 실제 `API_BASE_URL`이 필요하다. 실서버 주소가 없으면 실서버 연결 검증을 완료했다고 표시하지 않는다.
- 모드 전환은 재시작/재빌드 단위로 한다. 브라우저와 서버의 모드가 달라지는 런타임 토글은 추가하지 않는다.
- 캐시 키와 목업 저장소는 모드·세션·기능 단위로 구분하고 로그아웃/계정 변경 시 정리한다. Node MSW의 사용자 상태를 모든 방문자에게 공유하지 않는다.
- 실제 인증·주문·결제와 목업 신원·주문을 분리한다. 네이버 목업 로그인은 실제 백엔드 토큰을 발급한 것으로 처리하지 않으며, 해당 시연 세션의 인증 의존 요청은 MSW로 처리한다.
- 실제 상품에 대한 목업 부가기능 상태는 별도 저장한다. 목업 옵션 가격이나 쿠폰 금액을 실제 결제 금액에 합성하지 않는다. 미지원 구매 흐름을 시연할 때는 주문부터 결제 결과까지 격리된 목업 흐름을 사용하고 화면에서 시연임을 표시한다.
- 기존 운영 배포의 전체 목업 인증 차단을 무조건 제거하지 않는다. API 모드의 제한된 미구현 기능 핸들러와 전체 목업 시연 환경의 배포 정책을 구분한다.

## 확인된 적용 항목

| 영역 | 적용 내용 |
| --- | --- |
| 회원/인증 | 이메일·가입·로그인·refresh·카카오는 실제 계약 유지. 미구현 네이버는 격리된 MSW 시연 세션 제공 |
| 상품 | 목록·상세·카테고리·소분류 실제 연결 유지. 소재 목록은 `subcategoryId`와 `string[]` 계약으로 연결 |
| 소재 필터 등 | 소재 조회와 상품 검색 필터의 구현 여부를 따로 판정. 미지원 검색 조합은 MSW 결과로 명시하며 실제 검색이 된 것처럼 표시하지 않음 |
| 후기 | 실제 조회/등록 유지. 공개 이미지 ID는 임의 URL로 만들지 않음. 사진 표시 계약이 없는 부분은 표시 영역에 한해 시연 데이터임을 구분 |
| 문의 | 비밀 답변 노출 문제가 있는 공개 API를 그대로 노출하지 않음. 구현돼도 사용 불가한 계약은 근거를 목록에 기록하고 MSW 시연으로 연결 |
| 장바구니/주문/결제 | 구현된 API의 서버 금액·상태를 유지. 모든 목업 동작은 MSW로 제공. 미지원 옵션·할인·무통장 흐름은 격리된 시연 거래로 표시 |
| 교환/반품 | 실제 `ReturnData` 응답을 검증하고 접수 정보로 처리 |
| 마이페이지 | 프로필·설정·주소·주문·찜·최근 본 상품·후기를 전수 대조. 미구현 기능은 목록에 명시하여 MSW 연결 |
| 기타 문서 API | 모든 항목을 구현됨/미구현/구현됐지만 제한 있음/현재 화면 없음/서버 내부용으로 분류. 내부용·웹훅을 브라우저 호출로 노출하지 않음 |

## 완료 검증

- 문서의 모든 API 항목에 연결 상태와 근거가 있으며 누락 항목이 없다. 현재 화면이 없는 항목을 연결 완료로 세지 않는다.
- MSW 모드에서는 애플리케이션 API 요청이 실제 백엔드로 새지 않는다. 목업 미등록 요청은 테스트에서 실패한다.
- API 모드에서는 구현된 요청이 MSW에 가로채이지 않고, 미구현 목록의 요청만 MSW로 처리된다.
- 실제 API의 오류·빈 값·잘못된 응답을 목업 성공으로 바꾸지 않는다.
- 두 모드의 서버 렌더링과 브라우저 화면이 일치한다. 새로고침·로그아웃·계정 전환에서도 데이터가 섞이지 않는다.
- 목업 신원/주문으로 실제 인증 요청·결제 승인을 수행하지 않음을 테스트한다.
- typecheck, lint, 전체 단위 테스트, build 및 양쪽 모드의 주요 화면 E2E를 통과한다. 실제 외부 OAuth/메일/PG 성공 여부는 별도로 기록한다.

## 구현 순서

1. 전체 API-화면 연결 목록과 모드 판정/상태 분리 기반을 만든다.
2. 현재 화면의 실제 API 누락·응답 변환을 수정한다.
3. 미구현 기능과 기존 로컬 시연 동작의 MSW 핸들러를 연결한다.
4. 화면의 API 전용 숨김/차단 분기를 기능별 소스 판정으로 교체한다.
5. 양쪽 모드 회귀 검증과 문서를 갱신한다.

이 문서는 구현 전 설계이며, 상세 구현 계획과 제품 코드 변경은 설계 검토 이후 진행한다.
